# Connect IQ: what a data field can read about the native course, and how existing apps get route data onto the watch

Scope note: developer.garmin.com, forums.garmin.com, apps.garmin.com, dynamic.watch, support.komoot.com, trailforks.com, dcrainmaker.com and the5krunner.com were all blocked by the egress proxy (verified). API facts below come from two GitHub mirrors of the official SDK API docs. The older one is `tkafka/garmin-sdk-docs-for-ai`, a markdown copy with the footer "Generated Dec 11, 2024" and API levels up to 5.0.1. The newer one is `ztuskes/garmin-documentation-mcp-server`, an HTML copy with the footer "Generated Aug 11, 2025", which matches the SDK 8.2.x timeframe. Forum and store content comes only from search-result snippets and is marked as such. I found no API doc mirror newer than Aug 2025, so any additions from late 2025 to 2026 are unverified (see Gaps).

## Q1. Toybox.Activity.Info course/navigation members: names, types, API levels, semantics, availability on fēnix 7/8

### Takeaway
Activity.Info has 10 navigation members, all "Since API Level 2.1.0": `distanceToDestination`, `distanceToNextPoint`, `elevationAtDestination`, `elevationAtNextPoint`, `nameOfDestination`, `nameOfNextPoint`, `offCourseDistance`, `bearing`, `bearingFromStart` and `track`. All are nullable scalars. fēnix 7 and fēnix 8 (43mm, 47/51mm and Solar) are in the supported-device lists. "Next point" is best read as the next course point or turn, not the next track point. Forum reports show these fields have been buggy on some firmware (for example, distanceToDestination returning the distance to the next point).

### Cited Findings
Exact signatures and descriptions, verbatim from the SDK doc mirror:
- `var distanceToDestination as Lang.Float or Null`: "The distance to the destination in meters (m)." Since API Level 2.1.0. — [SDK doc mirror, Activity/Info.md (Dec 2024)](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Activity/Info.md)
- `var distanceToNextPoint as Lang.Float or Null`: "The distance to the next point in meters (m)." Since API Level 2.1.0. — [same](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Activity/Info.md)
- `var elevationAtDestination as Lang.Number or Null`: "The elevation at the destination in meters (m)." Since API Level 2.1.0. **Note that the type is Number (integer), unlike `elevationAtNextPoint`, which is a Float.** — [same](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Activity/Info.md)
- `var elevationAtNextPoint as Lang.Float or Null`: "The elevation at the next point in meters (m)." Since API Level 2.1.0. — [same](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Activity/Info.md)
- `var nameOfDestination as Lang.String or Null`: "The name of the destination." Since API Level 2.1.0. — [same](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Activity/Info.md)
- `var nameOfNextPoint as Lang.String or Null`: "The name of the next point." Since API Level 2.1.0. — [same](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Activity/Info.md)
- `var offCourseDistance as Lang.Float or Null`: "The distance to the nearest point on the current course in meters (m)." Since API Level 2.1.0. — [same](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Activity/Info.md)
- `var bearing as Lang.Float or Null`: "The current bearing in radians. Bearing is the direction from your current location or position to the destination of navigation, dependent on your current location." Since API Level 2.1.0. — [same](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Activity/Info.md)
- `var bearingFromStart as Lang.Float or Null`: "Bearing from start is the direction of desired track from the start of navigation to the destination in radians. This is only dependent on your location when a course is set, and it is not dependent on where you may have moved to during an activity." Since API Level 2.1.0. — [same](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Activity/Info.md)
- `var track as Lang.Float or Null`: "The current track in radians. Track is the direction of travel in radians based on GPS movement. If supported by the device, this provides compass orientation when stopped." Since API Level 2.1.0. `track` is the direction of travel, not the course polyline. — [same](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Activity/Info.md)
- Related members: `currentLocation` and `startLocation` (`Position.Location or Null`, API 1.0.0). "This member will always provide a `null` value unless the Positioning Permission is enabled." — [same](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Activity/Info.md)
- The Aug 2025 mirror has the same 10 members with the same types and "Since API Level 2.1.0". Each supported-device list includes "fēnix® 8 43mm", "fēnix® 8 47mm / 51mm" and "fēnix® 8 Solar" variants, and also fēnix 7, epix Gen 2/Pro and Forerunner 955/965. — [SDK doc mirror, Activity/Info.html (Aug 2025)](https://github.com/ztuskes/garmin-documentation-mcp-server/blob/main/docs/Toybox/Activity/Info.html)
- Older forum claim (probably 2017–2018): these fields are "only available on advanced navigation devices such as the 935 and Fenix 5, but not on devices like VA3 or 645". — search snippet, [Garmin forum: Access course data from data field](https://forums.garmin.com/developer/connect-iq/f/discussion/303652/access-course-data-from-data-field) / [Accessing course data](https://forums.garmin.com/developer/connect-iq/f/discussion/3738/accessing-course-data)
- Bug report (old): "Under certain circumstances, ActivityInfo::distanceToDestination seems to have the same value as distanceToNextPoint, instead of reflecting the distance to the end of the course." A Garmin reply said it was "fixed on fenix 5 Plus and Forerunner 935", and later users reported the same thing on fēnix 6 while following a course. — search snippet, [Garmin forum bug report](https://forums.garmin.com/developer/connect-iq/i/bug-reports/activityinfo-distancetodestination-seemingly-incorrect-reflects-distance-to-next-point-not-distance-to-end-of-course)
- Old (2016-era) forum hearsay: on Edge 520 firmware 7.2, `nameOfNextPoint` returned only null even when the course had course points, while distance-to-next worked. Course data was said at first to be accessible only on the Oregon series. — search snippet, [Garmin forum: Accessing course data](https://forums.garmin.com/developer/connect-iq/f/discussion/3738/accessing-course-data)
- Forum hearsay: "Course point titles are not available to Connect IQ apps." Whether course-point type data reaches CIQ depends on firmware. — search snippet, [Garmin forum: Display of Course Point Turn Arrow](https://forums.garmin.com/developer/connect-iq/f/app-ideas/5759/display-of-course-point-turn-arrow) (the snippet did not make clear which thread this came from)
- On native fields, fēnix 6 users report that "Next Waypoint" and "Distance to Next" show the distance to the next turn when following a course. This fits "next point" meaning the next course point or turn (which may be auto-generated), not the next GPX trackpoint. — search result title, [Garmin forum fēnix 6](https://forums.garmin.com/outdoor-recreation/outdoor-recreation/f/fenix-6-series/192222/next-waypoint-and-distance-to-next-showing-distance-to-next-turn)
- Real-world use while following a native Course: the open-source climbBrooo data field computes distance-along-course as `routeTotalLen - info.distanceToDestination`. Its code comment says: "when the route is loaded as a Garmin course, distance-along-course (rtl - distanceToDestination) is a more accurate axis than the raw odometer". This implies that `distanceToDestination` is filled with the remaining distance along the course during Course navigation on current watches (developed for the Forerunner 255). — [climbBrooo garmin/source/ClimbProView.mc](https://github.com/SvenvanDalen/climbBrooo/blob/main/garmin/source/ClimbProView.mc)
- Other open-source fields that read these members, useful as on-device test tools: GRun (`source-highmem/GRunViewHighMem.mc`), hansiglaser/ConnectIQ ShowAllInfos, and ekutter/CIQTest DevTestFld. — GitHub code search for `elevationAtNextPoint` / `nameOfDestination` in `.mc`: [GRun](https://github.com/gcormier9/GRun), [hansiglaser/ConnectIQ](https://github.com/hansiglaser/ConnectIQ), [ekutter/CIQTest](https://github.com/ekutter/CIQTest)

### Inferences
- `elevationAtNextPoint` is the elevation of the next course point, not the next trackpoint. So it gives at most a sparse sample of the profile, one value per course point or turn, and nothing between points. It cannot be used to build a continuous profile.
- `distanceToDestination` is the best native hook for a fixed-scale profile field. With your own copy of the profile (distance→elevation), position along the course is roughly `totalLen − distanceToDestination`. This beats `elapsedDistance` when you start late, detour, or skip part of the course. climbBrooo shows this working in practice. Because of the old "equals distanceToNextPoint" bug, add a sanity check (see climbBrooo's length gate in Q3).
- "fēnix 8 AMOLED" should correspond to the non-Solar "fēnix® 8 43mm" and "fēnix® 8 47mm / 51mm" entries. The Solar models are listed separately as "fēnix® 8 Solar 47mm/51mm". This mapping is inferred from Garmin's product naming, not stated in the docs.

### Gaps
- No Garmin statement found that defines "next point" precisely (course point vs. waypoint vs. auto-generated turn), or whether `elevationAtNextPoint` is filled for auto-generated turn-guidance points on fēnix 7/8. Test on the device.
- No 2024–2026 source confirms that `nameOfNextPoint`, `nameOfDestination` or `elevationAtDestination` are non-null on fēnix 8 firmware while following a Course. The null reports are all old.
- Store and forum pages could not be fetched directly, so the forum claims above are secondhand search snippets.

## Q2. Is there any API (up to 2026) exposing the loaded course's track points, elevation profile, ClimbPro climbs, or total course distance?

### Takeaway
No. Up to the latest API docs I could verify (Aug 2025, SDK 8.2.x era), no Connect IQ API exposes the active course's geometry, elevation profile, ClimbPro climbs, or total length to a data field. Activity.Info only offers the scalar fields in Q1. `PersistedContent.Course` exposes only name, id, intent and remove, and is not available to data fields at all. Forum answers say plainly that you cannot draw the upcoming course elevation from native data.

### Cited Findings
- Activity.Info in the Aug 2025 mirror has 50 `var` members. None has an API level of 5.1 or higher, and none exposes course points, polyline, profile or climbs. A search of all Toybox modules for "course"/"climb" finds only the Q1 members, PersistedContent.Course, and unrelated floors-climbed fields. — [SDK doc mirror (Aug 2025), docs/Toybox](https://github.com/ztuskes/garmin-documentation-mcp-server/tree/main/docs/Toybox)
- Module list in that mirror: Activity, ActivityMonitor, ActivityRecording, Ant, AntPlus, Application, Attention, Authentication, Background, BluetoothLowEnergy, Communications, Complications, Cryptography, FitContributor, Graphics, Lang, Math, Media, Notifications, PersistedContent, PersistedLocations, Position, Sensor, SensorHistory, SensorLogging, StringUtil, System, Test, Time, Timer, UserProfile, WatchUi, Weather. There is no Navigation or Course module. — [same](https://github.com/ztuskes/garmin-documentation-mcp-server/tree/main/docs/Toybox)
- The Complications types (API 4.2+) contain nothing course-, navigation- or ClimbPro-related. The list includes ALTITUDE, FLOORS_CLIMBED, SUNRISE, WEEKLY_BIKE_DISTANCE and so on. — [SDK doc mirror, Complications.md](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Complications.md)
- `Toybox.PersistedContent` (API 2.2.0): "allows access to stored routes, waypoints, and other stored user data". Methods: `getCourses()`, `getRoutes()`, `getTracks()`, `getWaypoints()`, `getWorkouts()`, `getAppCourses()` (API 3.0.0) and friends, plus `saveWaypoint()`. The `Content` interface is only `getName() as String`, `getId() as Number`, `toIntent() as System.Intent`, `remove()`. `Course` is "A saved Course on the device in .FIT format". Permission: `PersistedContent`. — [SDK doc mirror, PersistedContent.md](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/PersistedContent.md); [Course.md](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/PersistedContent/Course.md)
- PersistedContent App Types: "Audio Content Provider, Glance, Watch App, Widget". **Data Field is not listed.** — [SDK doc mirror (Aug 2025), PersistedContent.html](https://github.com/ztuskes/garmin-documentation-mcp-server/blob/main/docs/Toybox/PersistedContent.html)
- `WatchUi.MapTrackView` (API 3.0.0; App Types include Data Field): "A View for rendering a map on the screen while tracking the current location of the device… This map will display the default navigation icons for the device". `WatchUi.MapView` (API 3.0.0) renders a static map with your own `MapMarker`/`MapPolyline`. Both draw maps only and expose no course data. fēnix 7/8 are supported. — [MapTrackView.html](https://github.com/ztuskes/garmin-documentation-mcp-server/blob/main/docs/Toybox/WatchUi/MapTrackView.html); [MapView.html](https://github.com/ztuskes/garmin-documentation-mcp-server/blob/main/docs/Toybox/WatchUi/MapView.html)
- Forum answers (Garmin forum, search snippets): "You can't access course data in a data field." "There's no way to plot the upcoming elevation… If you have a mapping-enabled watch, you can implement a data field which shows the map (and optionally, the breadcrumb trail), but not elevation." Another snippet: "There's only a handful of course-related fields in Activity.Info like distanceToDestination, courseOverGround, track, etc." — [Garmin forum: Access course data from data field (thread 303652)](https://forums.garmin.com/developer/connect-iq/f/discussion/303652/access-course-data-from-data-field)
- Forum snippet: "The API only gives access to the active activity stats, which doesn't include any positional information, including elevation" (of the course). Developers have been asking for course-point and profile access for years. — search snippet, [Garmin forum: Display of Course Point Turn Arrow](https://forums.garmin.com/developer/connect-iq/f/app-ideas/5759/display-of-course-point-turn-arrow)
- Connect IQ SDK 8.2.1 release notes, per search snippets, mention new sensor-listener options and actionable background notifications. The snippets show nothing about course or navigation data. — [Garmin forum: Connect IQ SDK 8.2 Now Available](https://forums.garmin.com/developer/connect-iq/b/news-announcements/posts/connect-iq-sdk-8-2-now-available); [the5krunner: Connect IQ 8 – what we know](https://the5krunner.com/2025/01/07/connect-iq-8-what-we-know-so-far-about-system-8/)

### Inferences
- Total course distance is not exposed directly. A proxy is the largest `distanceToDestination` seen near the start of navigation, or `elapsedDistance + distanceToDestination` while you are on course. climbBrooo's `navMaxToDest` does the first. This depends on the "distanceToDestination = remaining course distance" behaviour and on the old bug not coming back.
- ClimbPro climb data is completely closed to CIQ. A fixed-exaggeration profile field needs its own copy of the course profile.

### Gaps
- I could not check SDK versions released after Aug 2025 (such as 8.3/8.4 or a System 9 SDK in 2026). I found no search result announcing course or track-point access, but the official release notes and API docs could not be fetched.
- I found no official Garmin staff statement or roadmap item about exposing course geometry. The forum quotes above are from other developers, and the snippets did not name the author.

## Q3. Can a CIQ app read the name of the course being navigated? Can it be used to auto-select one of several embedded/downloaded courses?

### Takeaway
The only candidate is `Activity.Info.nameOfDestination` (String or Null, API 2.1.0). The docs describe it only as "The name of the destination". No source confirms that it holds the course name (rather than the last course point's name, or null) when following a Course on fēnix 7/8. Test it on the device. A more robust auto-select key that has been used in practice is route length: compare the maximum `distanceToDestination` at the start against each stored profile's length, optionally combined with the start position.

### Cited Findings
- `nameOfDestination as Lang.String or Null`, "The name of the destination.", Since API Level 2.1.0. — [SDK doc mirror](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Activity/Info.md)
- `nameOfNextPoint` has been reported as always null on some firmware even with course points present (old, Edge 520 fw 7.2). — search snippet, [Garmin forum: Accessing course data](https://forums.garmin.com/developer/connect-iq/f/discussion/3738/accessing-course-data)
- climbBrooo "length gate": while navigation trust is UNKNOWN, the field records `navMaxToDest` (the largest `distanceToDestination` seen this ride). It trusts the native-course axis only if `navMaxToDest >= routeTotalLen - tol`, where `tol` is a percentage of the length with a floor in metres. Otherwise it falls back to the odometer. A test case covers "A different/shorter course is loaded: distanceToDestination never approaches 8 km". — [climbBrooo garmin/source/ClimbData.mc](https://github.com/SvenvanDalen/climbBrooo/blob/main/garmin/source/ClimbData.mc); [garmin/test/ViewSmokeTest.mc](https://github.com/SvenvanDalen/climbBrooo/blob/main/garmin/test/ViewSmokeTest.mc)
- In climbBrooo the active route is chosen in a separate watch app, not detected from the native course. "The four watch apps have separate, isolated storage, so selecting an active route on the browse app is relayed through the phone to the datafields. Setting the active route/climb needs the phone reachable at that moment; the ride itself does not." — [climbBrooo README](https://github.com/SvenvanDalen/climbBrooo)
- A watch app or widget (not a data field) can list course names with `PersistedContent.getCourses()` → `Course.getName()`, and start native navigation with `System.exitTo(course.toIntent())`. — [SDK doc mirror, PersistedContent.md example](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/PersistedContent.md)

### Inferences
- If `nameOfDestination` returns the course name on fēnix 8, it would be the simplest key: store several profiles in Application.Storage, keyed by course name, and pick the one whose key equals `nameOfDestination`. This is unverified. Build a fallback that matches on (a) the maximum `distanceToDestination` ≈ stored length within ±1–2%, and/or (b) the distance from `startLocation`/`currentLocation` at the start to each stored profile's first point.
- Each CIQ app has its own storage (climbBrooo's README describes separate storage per app). So a "course picker" watch app cannot write directly into the data field's storage. Selection goes through the phone, through the data field's own settings, or through automatic matching inside the data field itself.

### Gaps
- No source (forum, GitHub code or blog) shows what `nameOfDestination` returns during Course navigation on fēnix 6, 7 or 8. No public .mc code found displays it with a comment about its content.

## Q4. Existing CIQ Store apps and open-source projects with route elevation profiles, upcoming climbs, or maps from routes: how the route reaches the watch, limits and complaints

### Takeaway
Every app that shows an upcoming route elevation profile or climbs keeps its own copy of the route. None reads the native course geometry. The copy arrives by one of three routes: (1) a vendor watch app with account login that downloads over the phone or Wi-Fi (komoot, dynamicWatch dwMap, Trailforks); (2) an Android companion app pushing data by Bluetooth phone-app messages into the data field's storage (Breadcrumb, climbBrooo); (3) a web platform API reached via `makeWebRequest` (tribly). Native-course apps (routeCourse, Trailforks, the Garmin Connect Courses API) only deliver a .FIT/.GPX course to the native navigator and draw no custom profile in a data field.

## Q5. GitHub implementations of route/profile download into CIQ storage, and the relevant platform mechanisms

### Takeaway
There are three workable delivery mechanisms, all with open-source examples. (1) Phone-app messages (`Communications.registerForPhoneAppMessages`) into `Application.Storage`: supported for data fields from API 3.2.0 and used by Breadcrumb and climbBrooo. (2) `makeWebRequest` from a background service or a watch app: data-field background processes have very little memory (~16 KB cited on the forums). (3) `makeWebRequest` with `HTTP_RESPONSE_CONTENT_TYPE_GPX/FIT` (API 2.2.0) turns a GPX/FIT into a native course, but only watch apps and widgets can then read it back through PersistedContent, and only its name.

### Cited Findings
- `makeWebRequest` `:responseType`: "If HTTP_RESPONSE_CONTENT_TYPE_FIT or HTTP_RESPONSE_CONTENT_TYPE_GPX is given, the system will attempt to download and parse a FIT or GPX file and store the contained data in the device, based on the contents of the file." `HTTP_RESPONSE_CONTENT_TYPE_GPX` = 2 and `..._FIT` = 3, both API Level 2.2.0. makeWebRequest itself is API 1.3.0 and "can be used when connected to WiFi or a mobile device over Bluetooth." — [SDK doc mirror, Communications.md](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Communications.md)
- PersistedContent note: "As a general rule, Fitness and Edge devices will support .FIT format. Outdoor devices will support .GPX format." The module "is typically used in conjunction with the Communications module to retrieve content of type .FIT and .GPX and later access it using the get methods". — [SDK doc mirror, PersistedContent.md](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/PersistedContent.md)
- Communications module App Types (Aug 2025): "Audio Content Provider, Background, Data Field, Glance, Watch App, Widget". — [SDK doc mirror, Communications.html](https://github.com/ztuskes/garmin-documentation-mcp-server/blob/main/docs/Toybox/Communications.html)
- `registerForPhoneAppMessages` is API Level 1.4.0 in the docs. Breadcrumb's readme states that data fields only get phone-app messages on devices with API 3.2.0 or newer: "those devices (<3.2.0 api) do not support phone app messages for datafields". climbBrooo's data field manifest uses `minApiLevel="3.2.0"` and calls `Comm.registerForPhoneAppMessages(method(:onPhoneMessage))`. — [SDK doc mirror](https://github.com/tkafka/garmin-sdk-docs-for-ai/blob/main/markdown/doc/Toybox/Communications.md); [breadcrumb-garmin readme](https://github.com/pauljohnston2025/breadcrumb-garmin/blob/master/readme.md); [climbBrooo ClimbProApp.mc](https://github.com/SvenvanDalen/climbBrooo/blob/main/garmin/source/ClimbProApp.mc)
- Forum and Garmin FAQ snippets: "a watch face or data field can't do communications itself, but the background process can", and "With a data field, the background process can be limited to as little as 16k for code and data." JSON responses take more than twice the response size once parsed, and `-403` (NETWORK_RESPONSE_OUT_OF_MEMORY) is a known failure. — search snippets, [Garmin FAQ: How do I create a CIQ background service](https://developer.garmin.com/connect-iq/connect-iq-faq/how-do-i-create-a-connect-iq-background-service/); [Garmin forum: makeWebRequest w/ json response](https://forums.garmin.com/developer/connect-iq/f/discussion/7510/problem-with-makewebrequest-w-json-response)
- `Application.Storage` is API 2.4.0 (from the mirror page's "Since"). climbBrooo stores its route in chunks (`Storage.setValue("onb_raw_lat_" + k, lat.slice(from, to))` etc.) to stay within per-value limits. — [SDK doc mirror, Application/Storage.html](https://github.com/ztuskes/garmin-documentation-mcp-server/blob/main/docs/Toybox/Application/Storage.html); [climbBrooo RawRouteStore.mc](https://github.com/SvenvanDalen/climbBrooo/blob/main/garmin-onboard/source/RawRouteStore.mc)
- GitHub code search for `makeWebRequest` + elevation/route in `.mc` found only three repos: pauljohnston2025/breadcrumb-garmin (`source/Settings.mc`), pauljohnston2025/breadcrumb-garmin-app (`source/Settings.mc`), and glandais/tribly (`garmin-app/source/ApiClient.mc`). — GitHub code search (query `makeWebRequest elevation route extension:mc`); [breadcrumb-garmin](https://github.com/pauljohnston2025/breadcrumb-garmin); [tribly](https://github.com/glandais/tribly)
- Breadcrumb ships several app types, "so that users can install 2 alongside eachother… if BreadcrumbDataField crashes from OOM… we can still navigate the planned route using LWBreadcrumbDataField". The watch-app variant "Supports more features on more devices (the app has larger memory limits than a datafield)". — [breadcrumb-garmin readme](https://github.com/pauljohnston2025/breadcrumb-garmin/blob/master/readme.md)

### Inferences
- For a personal fēnix 8 field, the options that avoid rebuilding per course, from most to least work:
  (a) **Settings string**: paste a compact encoded profile (for example, delta-encoded elevation every N metres) into the field's app settings from Garmin Connect Mobile or Garmin Express. No companion app, but settings strings have practical length limits, which I did not verify.
  (b) **Background `makeWebRequest`** from the data field to a personal URL (GitHub Pages / gist), storing the profile in Storage. Limited by the ~16 KB background memory, so profiles must be tiny, sent as plain text, or fetched in pages.
  (c) **A companion watch-app/widget in the same project**, which has more memory, fetches the profile and could also start the native course via `PersistedContent.getCourses()` → `toIntent()`. Caveat: the climbBrooo README says separate apps have separate storage, so the hand-off to the data field would need the phone, the settings, or a data field that fetches for itself.
  (d) **A phone companion app** (Connect IQ Mobile SDK, iOS or Android) pushing by phone-app messages, as Breadcrumb and climbBrooo do.
- Pairing the profile with the native course by `distanceToDestination` gives accurate positioning. The profile could be generated from the same GPX that is sent to Garmin Connect as a course.

### Gaps
- Exact limits on Application.Storage and settings-string size on fēnix 8 were not verified (docs pages blocked).
- Whether a data field and a watch app can share storage in one CIQ project (for example, via the same app ID with multiple entry points) was not checked. climbBrooo's statement covers only its own four separate apps.
